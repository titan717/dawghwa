# Decisions

Choices made without stopping to ask, each resolved toward the design system and the local-first rules. Newest phase last.

## Owner requests that touch the non-negotiables

| # | Request | Resolution |
| --- | --- | --- |
| D4 | "Login / signup" | Local only. Each profile is a reader account on the device: "Create reader" (name, colour, optional 4-digit PIN) and "Sign in" (pick a reader, enter the PIN if one is set). The PIN is a SHA-256 hash with a per-profile salt, stored in the profile record. It is a privacy curtain for shared devices, not security, and the UI says so. There are no servers, emails or passwords, because the API is read-only and the brief says "no accounts". |
| D5 | "Comment bar" in the reader | The API has no comments endpoint, and we may not change it. Comments are stored on the device, per profile and per chapter, and included in export/import. The sheet says plainly that they are private to this device. Top / Newest tabs and reactions follow the PDF. "Top" sorts by your own reactions and pins, since there is no audience. |
| D6 | "Remove top bar navigation" | The shell top bar is removed at every breakpoint. Phone: Home has an in-page brand row that scrolls away. Desktop: the sidebar already has Search and Profile. Title pages keep their own back header. |
| D7 | "Remove Discover from the bottom bar, add achievements" | Bottom nav: Home, Search, Library, Awards, Profile. The label is "Awards" because "Achievements" does not fit a 78px slot at 390px; the route is `/achievements` and the page title is "Achievements". Discover stays reachable from Search (Browse categories, a Discover link) and Home. When Rewards is off, the Awards slot shows Discover again. |
| D8 | Reader "scroll only" | Vertical scroll is the only layout. Single, double, direction, fit and tap-zone settings are removed, and stored values are ignored. |
| D9 | Reader top bar "stuck on top" | The top bar is always visible (fixed, safe-area aware) and tapping no longer hides it. On Android the status bar still hides while reading. |
| D10 | "Progress page bar on the bottom should be removed" | The bottom bar is gone. Chapter navigation moves to the end of the chapter (Next Episode card) and the chapter list in the top bar. A 2px reading-progress line stays along the bottom edge of the top bar, because it is part of the top bar and costs no space. |
| D11 | Rewards toggle scope | `settings.rewards` is a device setting like theme (same place the old "Show milestones" switch lived), migrated from `achievements`. Off hides every gamified surface; nothing is deleted because it is all derived. |
| D12 | Reward card placement | Reward cards appear at the top of the screen (toasts stay at the bottom), max two at once, auto-dismiss after `--dur-celebrate`, with a 44px close button. They never take focus and use `role="status"`. |
| D13 | Haptics | Success haptic for level-ups and series completion, light for the rest; skipped under reduced motion and on the web. |
| D14 | Where progression lives | Derived from the event log at read time instead of a new `xp` store. No DB version bump, nothing to migrate, export/import keeps it for free, and it cannot drift from reading history. "Clear history" removes progress records but not events, so XP is kept. |
| D15 | XP values | Chapter +10, new series +25, new genre +15, series complete +100, weekly quest +50. Level step cost is 60 + 40 x (level - 1), so 100 chapters lands around level 7 to 8. |
| D16 | What counts as "completed a series" | Only a completion the reader earned: reaching the end of the final chapter of a series the source lists as completed, with at least half its chapters read here. Marking "Completed" by hand still organises the library, but earns no XP or badge. Older completions without context are not counted retroactively. |
| D17 | Mascot variants per tier | The brief says "beagle"; the in-app mascot is the PDF collie (D2). The character is never redrawn, so tiers unlock an accessory emblem on the mascot (paw print, bookmark, compass, reading glasses, scroll, crown) rather than altered art. Names: Pup, Bookhound, Story Scout, Lore Keeper, Archivist, Legend. |
| D18 | Genre passport scope | The 14 headline Discover genres are always shown (stamped or "Try it", linking to that genre on Discover). Other genres appear once stamped. A stamp needs one finished chapter, not a save. |
| D19 | How weekly quests are generated | Three quests per ISO week (Monday start), one each from a discover, a read and an "any" slot. They're picked with a random generator seeded by profile id + week, using only the state from before the week started, so the set never reshuffles mid-week and is the same on every device that has the same export. Templates have a `since` date (comment quests start 23 Nov 2026), so past weeks don't change when new templates ship. |
| D20 | Quest rewards | Each quest is worth +50 XP plus progress toward cosmetics. The "react" quest counts distinct titles and can complete once a week, so it can't be farmed. Progress comes from first-time chapter finishes only (same rule as XP). |
| D21 | Cosmetics storage | Unlocks (avatar frames and mascot emblems, gated by quest count or level) are derived from progress. Only the equipped choice is stored, in `profile.cosmetics`, which export/import carries. |
| D22 | Reading rhythm instead of streaks | Opt-in weekly target (Off/2/3/5 reading days), stored as `profile.rhythm`. It counts lifetime weeks met and never shows a broken streak, so missing a week costs nothing. |
| D23 | New signals | `surprise_pick` and `comment` are logged for quests but have recommender weight null, so they don't skew recommendations. `/?surprise=1` runs Surprise me so a quest can link to it directly. |
| D24 | Comments storage | New `comments` IndexedDB store (DB v2, additive migration with a unit test that upgrades a real v1 database). Keyed `[profileId, id]`, with a `byChapter` index. Export format v2 adds `comments`; v1 files still import. "Margin notes" counts distinct chapters commented on, taken from the event log, so deleting and re-posting can't farm it. |
| D25 | Comment features | Matches the PDF: Top / Newest tabs, TOP pill (pin), replies one level deep, thumbs up/down (your own vote), a ⋮ menu (pin, edit, delete with inline confirm), and an emoji row + "Leave a comment" composer pinned to the sheet bottom. 500-character cap. The open state is in the URL (`?comments=read|write`) so it survives reloads and can be deep-linked. |
| D26 | Chapter-end reward beat | While the Reader is open it takes over the reward sink, so XP, level ring, quests, unlocks, badge tiers and passport stamps appear as one static card in the end panel instead of a floating toast. Series completion adds the full mascot. Auto-next counts down 8s (it was 5s) so the beat can be read, and pauses while comments are open. |
| D27 | Series progress rings | Title cards and Continue Reading show a ring for highest chapter read / latest chapter, only when both are known and Rewards is on. The Continue card keeps its chapter-progress bar; the ring wraps the play button. |
| D28 | Collection complete | Derived: a collection with 2 or more series, all marked Completed. It is celebrated only on a change seen while the app is running (never on load), once per session. |
| D29 | Local sign-in, as built | `profile.pin = { salt, hash }` (SHA-256 of salt + PIN, 16-byte random salt). An unlock lasts for the browser session (`sessionStorage`), so a reload doesn't ask again but closing the app does. The Shell, Reader and Onboarding render a "Who's reading?" screen instead of content while the active profile is locked, so switching to a PIN profile from Profile asks for the PIN before anything shows. "Sign out" locks every profile and shows the reader list. Wrong PINs show an inline message and never lock you out (no punishment). There's no "forgot PIN" reset because there's no server; the hint says it isn't encryption. A blank, unused first-run profile is removed when you sign in as another reader or restore a backup. |
| D30 | PIN in export/import | Carried. A backup file of a PIN-protected reader stays PIN-protected after import, so moving devices doesn't silently drop the curtain. A malformed `pin` in a file is dropped rather than locking the profile forever. |
| D31 | Onboarding shape | Follows PDF pages 9 to 14: the collie talks in a speech bubble on every step, one question per screen, progress dots, Back/Cancel + Continue in a sticky footer, "N selected" for genres, and a final "Your experience is ready!" screen. Steps: Hello (Create reader / Sign in as another reader / Restore from a backup file) → name, colour, optional PIN → genres → formats → avoid → ready. Genre tiles use the existing lucide icons on tinted tiles instead of photos, because we have no licensed genre art and covers would mean extra API calls. `?edit=1` shows only the three taste steps; `?new=1` skips the hello step. The "finding stories" beat is replaced by the ready screen. |
| D32 | First quest and monthly recap | The ready screen shows the first unfinished weekly quest from the same seeded quest book (D19) with its real action, so onboarding hands off to something concrete. Hidden when Rewards is off (then "Start reading"). The monthly recap on Profile is derived from the farm-proof XP ledger (first completions only): chapters, new series, completions, reading days, XP (only with Rewards on), most-read series and genres with "new" stamps. The comparison line is neutral ("A calmer month than the one before. That counts too."). |
| D33 | Reader card | A 1080x1350 PNG drawn on a canvas, using colours read from the live CSS tokens so it matches the theme. It contains name, avatar colour, level and tier (only with Rewards on), totals, top 4 genres and the 12-week grid, and no titles or history. Shared with `@capacitor/share` + `@capacitor/filesystem` (cache dir) on Android, Web Share with files where supported, otherwise downloaded. The drawing code is lazy-loaded from Profile. `@capacitor/filesystem` is the one new native dependency. |
| D34 | Quest seed survives import (fix to D19) | Found while testing D30: importing gave the profile a new id, and quests were seeded by id, so a different set of quests could appear (and complete) after a move. Profiles now carry an optional `questSeed`; import keeps the original (`questSeed ?? id`), and existing profiles keep using their id, so nobody's current week changes. New profiles get a random seed, so their exports never contain the profile id; for older profiles the seed is the id, which is a random local UUID. |
| D35 | Accessibility gate | `e2e/a11y.spec.ts` runs axe-core (WCAG 2.0/2.1 A and AA tags) on Welcome, the reader step, Home, Search, Library, Achievements, Profile, About and the sign-in screen, in dark and light, at 390px and 1440px. Serious and critical violations fail CI. Moderate and minor ones are left to review, since axe flags some deliberate patterns (for example, decorative mascot art). |
| D36 | Accessible names contain the visible label | Fixes for axe `label-content-name-mismatch` (WCAG 2.5.3): bottom-nav items are named "Awards: Achievements" so voice users can say what they see. Cosmetic buttons and passport stamps drop their aria-label in favour of visible text plus `aria-pressed` or a screen-reader-only ", stamped" / ", not stamped yet" suffix. |
| D37 | Rewards-off contract is tested | An e2e test turns Show rewards off and asserts that no quest strip, card rings, Continue ring or level card render. This makes the "gamification is optional" rule a regression test rather than a promise. |
| D38 | Lighthouse without a CI budget, for now | A local Lighthouse 12 run on the production build is recorded in CONTINUATION. It's not a CI gate yet because the scores depend on the live API and network. The SEO score is low on private screens on purpose (noindex) and because local builds have no `SITE_URL` for the sitemap line. |
| D39 | Merge with the unified reading engine (PR #15) | PR #15 landed on main during Phase 5. The merge keeps its `questSeedOf()` (a derived seed, never the raw id, for old profiles) and keeps Phase 5's PIN. Import keeps a valid incoming seed (up to 64 chars) and otherwise uses the new profile's random seed. The reader stays behind the sign-in gate. |

## UI polish (2026-11, phases 1-4)

The brief: bring Dawghwa's UI up to the polish of WEBTOON / Tapas / MangaDex. Visual and interaction work only, no new data sources, no API changes. One branch and PR per phase.

| # | Topic | Decision |
| --- | --- | --- |
| D40 | How each phase is checked | `scripts/qa/ui-shots.mjs` captures every touched screen at 390px and 1440px in dark and light, before and after. `scripts/qa/cls.mjs` adds up layout shift per route. The Lighthouse and CLS baseline is `main` built and served the same way on the same machine, not production, because production is served from a CDN and the numbers can't be compared. |
| D41 | Hero contrast, measured | `--art-fade` is stronger in its middle stops (it reaches 0.82 black at 64% of the slide height, where the copy starts), and the desktop side fade is now a token (`--art-fade-side`) instead of a hardcoded gradient. `scripts/qa/hero-contrast.mjs` hides the copy, reads the real pixels behind each text box on every slide, and checks the actual text colour against the lightest 2% of them. Worst case: 6.66:1 (lime kicker, light theme, 390px). The title needs 3:1 as large text, everything else 4.5:1. |
| D42 | Hero motion | The active slide's key art drifts slowly (`--dur-drift` 22s, push-in to `--drift-scale`), using the separate `scale`/`translate` properties so it stacks on the desktop blur `transform`. Scroll parallax is added only where CSS scroll timelines exist, so it costs no JS. Arrows and dots move the track with a requestAnimationFrame tween (`--dur-slide` 420ms, `--ease-out`) instead of the browser's smooth scroll, whose timing varies. Scroll-snap is paused while the tween runs (`[data-tweening]`), and a wheel or touch cancels it. Under reduced motion every one of these is `animation: none` (the global 0.01ms rule would otherwise leave the art stuck on its last frame) and the tween jumps straight to the target. |
| D43 | Shelf scrolling | Native momentum scrolling and `proximity` snap stay as they are. "Smoother" means not fighting the platform. The arrows now land with a card's leading edge on the track padding (`shelfTarget`), so you never stop mid-card. |
| D44 | Card hover and focus (amends D27) | The cover lifts with `--lift` and gets `--shadow-lift` on hover and `:focus-visible`, and presses to 0.97. Only transform and box-shadow change, so nothing reflows. On pointer devices the series ring (still Rewards-only) shows up on hover and focus. On touch, where there is no hover, it stays visible. Titles are already always shown under the cover, so they aren't revealed again on top of the art. The title box always reserves two lines, so rows line up whether a title wraps or not. |
| D45 | New-chapter badge, unread pill, progress bar | "Up" (vermilion sticker) shows only when the title's `updatedAt` is within 3 days. Catalogue lists don't carry `updatedAt`, so it's rare there, and that's honest. The vermilion "N new" pill is floor(latest) minus floor(highest read), shown only when both numbers are known. The bar along the cover's bottom edge is highest read / latest. It counts as reading state, not gamification, so it ignores the Rewards switch. Cards that already have a chapter bar (Continue reading) don't get a second one. |
| D46 | Discover density | Masonry was turned down. Covers are a fixed 5:7, so a masonry layout would look just like a grid and only add complexity. The toggle switches between "Large covers" and "Compact" (about 3 per row on a phone, no meta line). It's a device setting (`settings.gridDensity`), stored the same way as theme, so it survives reloads. The two buttons are 44px wide. |
| D47 | Search feel | The result area turns into a skeleton grid on the first keystroke, before the 280ms debounce runs, so the screen reacts right away. Matched words in titles are wrapped in `<mark>` (lime tint, heavier weight). Structured searches ("completed fantasy manhwa") turn words into filters rather than text matches, so their results aren't highlighted. |
| D48 | Skeletons match the final layout | Skeletons are built from the real card classes (`.card-cover > .cover`, a two-line `.card-title`, `.card-meta`), and Home passes each section's layout, so ranked, wide and spread shelves get matching placeholders. CLS on Home, Discover and Search is the same as `main` (≤ 0.0004). |
| D49 | Bundle | The initial JS grew by 28 bytes gzip (147,282 to 147,310), from the title highlighter in the shared card. The motion helpers sit in the lazily loaded Home chunk. This is within the 150 KB budget and is recorded rather than worked around. |
| D50 | Read CTA that survives scroll | On phones the Start/Continue button already sits in a fixed bottom bar; it now gets a frosted chrome backdrop (`--blur-chrome`) so chapter rows stay readable under it. On desktop, once the hero button scrolls out of view (IntersectionObserver), a compact copy fades into the sticky tab bar. Only one is ever focusable: the hidden copy is `inert` plus `aria-hidden`. |
| D51 | Relative chapter times | Each chapter row shows a `<time>` with "2h ago" / "3d ago" / a date after a year, and the exact date in its title and `dateTime`. Some providers send their own relative text ("7y ago"); that's shown unchanged rather than guessed into a date. The label is computed at render, not ticking, so rows never reflow while you look at them. |
| D52 | Volume groups | Chapters are grouped under "Volume N" headers only when at least half have a volume, there are 2 or more distinct volumes and no search is active. Otherwise the headers would be noise. Headers are rows of the same 56px height inside the existing virtualized list, so virtualization and scroll math are unchanged. |
| D53 | Jump rail | Lists with 60 or more rows get a sticky "Jump to chapters" rail: volumes when grouped, otherwise ranges of 50 (100 for very long lists). Buttons are 44px high and the one in view is `aria-current`. Ranges follow the list's sort order, so they read numerically either way. |
| D54 | Provider picker | There was no picker before, so one was built from data the title page already loads (`data.sources`), not a new request. Readable sources are radios ("Available · latest ch. N"); sources that failed or had no match are plain text with a ban icon, a dashed frame, struck-through name and a reason ("No match found"), so the difference is shape and text, not opacity. Still-loading sources show a spinner and "Checking…". Picking a source filters the list to chapters it has and makes it the preferred version. It only shows on unified titles with 2 or more sources. |
| D55 | Tabs: sliding ink and swipe | The selected-tab underline is one element moved with `--ink-x`/`--ink-w` (measured in a layout effect and on resize) and a spring-like `--ease-spring` transition. On touch, a fast horizontal flick on the panel (over 64px, mostly horizontal, under 600ms) moves to the next or previous tab, with a light haptic. Flicks that start in inputs or horizontal scrollers are ignored, and `touch-action: pan-y` keeps vertical scrolling native. The new panel slides in from the swipe direction; under reduced motion it just appears. |
| D56 | Banner and cover | On desktop the blurred cover becomes a 460px banner behind the hero that dissolves into the page (`--tp-backdrop-fade`, per theme). The cover gets a printed-volume stack behind it, a layered `--shadow-cover`, and a folded corner that lifts on hover (`--peel` to `--peel-hover`; stays put under reduced motion). The loading skeleton keeps the cover's footprint without the print treatment. |
| D57 | Hero order | Cover, kicker, title, credit, stats, your progress, then the CTA, reactions, synopsis, tags and "why you might like it". Reading is the main job of the page, so the button now comes before the long text. |
| D58 | Title-page contrast, measured (and what it caught) | `scripts/qa/title-contrast.mjs` makes every piece of text on the title page transparent, reads the real pixels behind it (banner art, cover shadow, stripes) and compares the real text colour with the worst 2% of them. Its first run found 6 real failures: muted text over the desktop dark banner, the light kicker sitting in the cover's shadow, and the light warning banner over its stripes (the light `--warn` was 4.5:1 on `surface-2` with no margin). Fixes: a stronger top of `--tp-backdrop-fade`, a shorter light `--shadow-cover`, and light `--warn` #7a4f00 (5.4:1, used everywhere). It now passes at 390 and 1440 in both themes; tightest is 4.77:1. The axe gate now covers the title page too, which found three older name mismatches (synopsis, sort and versions buttons). Their names now contain their visible text. |
| D59 | Title-page performance | Initial JS is unchanged (143.9 KB gzip); the work is in the lazily loaded title-page chunk and CSS. CLS on the title page is at or below `main` (390: 0.0149 to 0; 1440: 0.0242 to 0.0203). Lighthouse on the title page over three runs each: performance 68 to 72 on both (`main` median 72, branch 69), TBT 430 to 590 ms on `main` and 500 to 570 ms on the branch, which is inside run-to-run noise against the live API. Accessibility and best practices are 100 on both. |
